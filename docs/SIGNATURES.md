# 광고 패킷 복합 필터

회사 ID가 같다는 이유만으로 스마트안경 후보로 올리지 않도록, **회사 ID + 필수 서비스 UUID 전체 + 제조사 페이로드의 마스크 바이트 패턴**을 함께 대조합니다. 외부 수신기에서 가져온 v2 자료에 사용자가 제공한 규칙을 적용하는 기능입니다. 브라우저의 기본 BLE 선택창은 이 원자료를 제공하지 않습니다.

현재 배포본에는 **실기기로 검증된 스마트안경 규칙이 없습니다.** 예제는 가상의 회사·UUID·패턴으로 엔진 동작을 보여줍니다. 규칙의 형식을 검사하는 것과 실제 기종을 검증하는 것은 다릅니다. 출처 링크가 있어도 앱이 그 근거의 진위를 인증하지 않습니다.

## 사용 순서

1. 구역별 신호 비교에서 **복합 필터 예제**를 누르면 가상 자료 3종을 대조합니다. 복합 조건 일치, 같은 회사지만 다른 패턴, 미등록 회사를 각각 표시합니다.
2. 현장 자료를 대조하려면 수신기 관측을 `examguard.radio.v2` 형식으로 변환하여 **측정 파일 열기**로 불러옵니다.
3. 해당 기종과 수집 조건을 검증한 `examguard.signatures.v1` 파일을 **규칙 파일 열기**로 불러옵니다.
4. 일치 근거와 규칙 출처를 확인하고 B·C 모드로 실물을 대조합니다. 보고서는 비연습 자료와 비연습 규칙의 분석만 포함합니다.

## 광고 입력 v2

기본 필드·용량·RSSI 조건은 [RADIO_FORMAT.md](RADIO_FORMAT.md)와 같습니다. 각 sample에 다음 `advertisement`를 추가합니다. **하나의 sample은 한 번의 광고 관측**이어야 하며, 서로 다른 시각의 패킷·스캔 응답을 합치지 마세요. 수신기 SDK가 누적한 결과라면 원자료를 분리하거나 입력에서 제외해야 합니다.

```json
{
  "schema": "examguard.radio.v2",
  "source": "Fictional receiver / example only",
  "isDemo": true,
  "samples": [{
    "deviceKey": "session-example",
    "name": "Fictional glasses",
    "zone": "창가",
    "rssi": -64,
    "timestamp": "2026-11-07T09:00:00+09:00",
    "advertisement": {
      "manufacturerData": [{"companyId": 65535, "bytes": [0, 71, 16, 167, 1]}],
      "serviceUuids": ["f0f0f0f0-1111-4222-8333-444444444444"]
    }
  }]
}
```

`companyId`는 0~65535 정수입니다. `bytes`는 제조사 데이터에서 **회사 ID 2바이트와 AD 길이·유형을 제외한 데이터**입니다. 원시 AD 구조에서 회사 ID를 읽을 때는 little-endian으로 해석한 뒤 정수로 넘깁니다. `payload.offset: 0`은 이 `bytes`의 첫 바이트입니다. 회사 ID를 `bytes`에 다시 붙이면 오프셋이 맞지 않습니다.

제조사 항목은 관측당 최대 8개, 각 배열은 최대 512바이트(각 0~255 정수), UUID는 최대 32개입니다. UUID는 4·8자리 16진수 또는 하이픈이 있는 128비트 문자열을 받으며 Bluetooth 기본 UUID로 정규화합니다. `advertisement`가 없으면 해당 관측은 RSSI 비교에만 사용합니다. 두 배열이 모두 비어 있으면 원자료 없음으로 표시합니다. 알 수 없는 필드는 버립니다.

## 규칙 v1

```json
{
  "schema": "examguard.signatures.v1",
  "source": "Fictional demonstration rules",
  "isDemo": true,
  "rules": [{
    "id": "fictional-glasses-v1",
    "label": "가상 안경 후보",
    "companyId": 65535,
    "serviceUuids": ["f0f0f0f0-1111-4222-8333-444444444444"],
    "payload": {"offset": 1, "bytes": [71, 16, 160], "mask": [255, 255, 240]},
    "evidence": {
      "sourceUrl": "https://github.com/epoko77-ai/examguard/blob/main/docs/SIGNATURES.md",
      "model": "가상 제품",
      "notes": "실제 제조사나 실기기 자료가 아닌 테스트 예제입니다."
    }
  }]
}
```

규칙 파일은 256 KB 이하, 1~64개 규칙입니다. 각 규칙은 고유 ID, 표시 이름, 회사 ID, 1~16개 필수 UUID, 바이트 패턴, 모델·출처·메모를 모두 갖춰야 합니다. 회사 ID만 있는 규칙은 받지 않습니다. 출처는 인증정보 없는 HTTPS 주소만 허용하며 가져오거나 실행하지 않습니다.

패턴은 1~64바이트, 오프셋은 0~511이며 패턴 끝은 512를 넘지 않습니다. 마스크를 생략하면 모든 비트를 비교합니다. 지정하면 패턴과 길이가 같아야 하며 전체 0 마스크는 거부합니다. 비교식은 다음과 같습니다.

```text
(관측값[offset + i] & mask[i]) == (규칙값[i] & mask[i])
```

위 예제의 마지막 바이트는 상위 4비트만 비교합니다. `0xA0`부터 `0xAF`까지 일치합니다. 바뀌는 필드를 무작정 가리면 오탐이 늘 수 있으므로 마스크의 근거를 기록해야 합니다.

UUID와 회사 ID·페이로드는 **같은 광고 관측**에서 충족해야 합니다. 회사 ID와 패턴도 같은 제조사 항목 안에서 일치해야 합니다. 다른 패킷의 UUID·바이트를 모아 일치로 만들지 않습니다. 같은 기기 키의 관측 중 하나라도 일치하면 후보로 표시하며, 서로 다른 기종 이름의 규칙이 일치하면 여러 후보로 남깁니다. 표시 횟수는 입력의 일치 관측 수이며 중복 입력을 자동 제거한 패킷 수가 아닙니다.

## 결과의 의미와 한계

| 표시 | 의미 |
| --- | --- |
| 복합 규칙 일치 후보 | 입력된 규칙의 세 조건이 일치. 기종 확정이나 촬영 증거는 아님 |
| 여러 기종 규칙 일치 | 서로 다른 기종 이름의 규칙이 일치하여 실물 구분 필요 |
| 회사 ID 일치 · 복합 조건 부족 | 회사는 같지만 규칙의 전체 조건이 충족되지 않아 후보로 올리지 않음 |
| 등록 규칙과 불일치 | 현재 규칙으로 식별하지 못함. 기기 부재·일반 안경·안전을 뜻하지 않음 |
| 광고 원자료 없음 / 대조할 규칙 없음 | 비교에 필요한 입력 부족 |
| 연습 규칙 · 현장 자료에 적용 안 함 | 연습 규칙으로 현장 기기를 분류하지 않음 |

엄격한 조건은 일부 오탐 경로를 막지만, 패킷에 UUID가 없거나 펌웨어가 패턴을 바꾸면 미탐이 늘 수 있습니다. 광고·스캔 응답을 따로 전송하는 기기는 현재 규칙으로 대조하지 못할 수도 있습니다. 정확도·오탐 감소율은 실제 제품·다른 전자기기·여러 연결 상태를 비교한 뒤 평가해야 합니다.

`isDemo: false`는 사용자의 자료 구분이며 검증 인증이 아닙니다. 공개 예제의 플래그만 바꾸어 실기기 규칙으로 쓰지 마세요. 기여 시 기종·펌웨어·전원/페어링 상태, 수신기 종류, 수집 방법, 같은 회사 다른 제품의 비교 결과를 포함하세요. 원자료의 식별 가능한 바이트는 [개인정보 안내](PRIVACY.md)에 따라 검토해야 합니다.
